Del Querying al Diseño

Por qué un técnico necesita modelar, no solo consultar

Ya sabés hacer SELECT, JOIN, GROUP BY y subconsultas sobre la base TechPlay Store. Pero ahora la pregunta es: ¿quién diseñó esa base de datos? ¿Cómo supo qué tablas crear y cómo relacionarlas?

Lo que distingue a un Técnico Completo
Un operador sabe consultar datos. Un técnico sabe diseñarlos: analizar un negocio real, elegir las tablas, definir los campos, establecer las relaciones y garantizar que no haya información duplicada ni inconsistente.

Imaginá que te contratan para el sistema de una nueva sucursal de TechPlay Store. No te dan la base hecha: te dan las reglas del negocio. "Una venta puede tener varios productos. Un producto pertenece a una sola categoría." Tu trabajo es convertir esas reglas en tablas SQL. Ese proceso se llama Modelado de Datos.

La Clave Primaria (PRIMARY KEY)

🔑

El "documento de identidad" de cada fila

Identifica de forma única e irrepetible cada registro. Reglas: valores únicos, nunca NULL, estable en el tiempo. La práctica más recomendada es usar id_nombre_tabla INT AUTO_INCREMENT. MySQL asigna el número automáticamente al insertar.

-- Tabla bien diseñada: PK artificial con AUTO_INCREMENT
CREATE TABLE productos (
    id_producto   INT           AUTO_INCREMENT PRIMARY KEY,
    nombre        VARCHAR(120)  NOT NULL,
    precio        DECIMAL(10,2) NOT NULL,
    stock         INT           NOT NULL DEFAULT 0
);

⚡ Regla de Oro
Nunca uses VARCHAR donde debería ir INT. Las claves primarias y foráneas siempre son INT. Guardá texto en VARCHAR solo cuando el valor tenga contenido alfanumérico real.

1 : 1 Relación Uno a Uno

Cada registro de la tabla A tiene exactamente un registro en la tabla B, y viceversa. Se usa para "extender" una tabla con datos específicos de un subconjunto.

En TechPlay Store: La tabla productos guarda todos los artículos. Para las consolas (solo ellas), necesitamos datos técnicos muy específicos: resolución, chip, watts. Crear una tabla separada datos_tecnicos_consolas evita dejar cientos de campos NULL en los juegos y accesorios.

La FK id_producto en datos_tecnicos_consolas tiene restricción UNIQUE → garantiza el 1:1

📍 ¿Dónde va la FK en 1:1?
En la tabla que representa el "detalle" o "extensión". En nuestro caso: datos_tecnicos_consolas.id_producto → productos.id_producto. Además, esa FK debe ser UNIQUE para que dos fichas no apunten al mismo producto.

Guía de clics en Workbench

1
Abrí el editor EER: File → New Model → doble clic en Add Diagram.
2
Creá ambas tablas con el ícono Place a New Table en la barra lateral.
3
En la tabla hija, activá la opción UQ (Unique) en el campo id_producto. Esto es lo que garantiza el 1:1.
4
Seleccioná 1:1 Non-Identifying Relationship en la barra lateral.
5
Clic en la tabla hija primero (datos_tecnicos_consolas), luego en la tabla padre (productos). Workbench dibuja la relación.
6
Para generar el SQL: Database → Forward Engineer.
-- Relación 1:1: productos → datos_tecnicos_consolas
CREATE TABLE datos_tecnicos_consolas (
    id_tecnico     INT          AUTO_INCREMENT NOT NULL,
    id_producto    INT          NOT NULL,
    resolucion_max VARCHAR(20)  NULL,
    chip_grafico   VARCHAR(60)  NULL,
    consumo_watts  INT          NULL,
    certificacion  VARCHAR(40)  NULL,
    puertos_usb    INT          NULL,
    PRIMARY KEY (id_tecnico),
    -- UNIQUE garantiza el 1:1:
    UNIQUE INDEX uq_id_producto (id_producto ASC),
    CONSTRAINT fk_tecnico_producto
        FOREIGN KEY (id_producto)
        REFERENCES productos (id_producto)
        ON DELETE CASCADE ON UPDATE CASCADE
);

1 : N Relación Uno a Muchos — La más frecuente

Un registro de A puede relacionarse con múltiples registros de B, pero cada registro de B pertenece a un único A. Es el patrón más común en cualquier BD del mundo real.

En TechPlay Store: 1 categoría → N productos · 1 cliente → N ventas · 1 proveedor → N productos

La FK siempre va en la tabla del lado N. Un producto tiene UNA categoría; una categoría tiene MUCHOS productos.

📍 ¿Dónde va la FK en 1:N?
Siempre en la tabla del lado N (la tabla "hija"). Si una categoría tiene muchos productos → id_categoria va en productos, nunca al revés. La tabla padre (categorias) no necesita ningún campo adicional.

Guía de clics en Workbench

1
Con ambas tablas en el diagrama, seleccioná 1:N Non-Identifying Relationship en la barra lateral.
2
Hacé clic primero en la tabla hija (productos, la que tendrá la FK), luego en la tabla padre (categorias). El orden es fundamental.
3
Workbench genera id_categorias en productos. Renombralo a id_categoria haciendo doble clic sobre la tabla.
4
Verificá la relación: doble clic sobre la línea → panel de propiedades. Podés editar el nombre de la FK y las opciones On Delete / On Update.
-- Relación 1:N: categorias (padre) → productos (hija)
CREATE TABLE productos (
    id_producto   INT           AUTO_INCREMENT NOT NULL,
    nombre        VARCHAR(120)  NOT NULL,
    -- FK al padre (lado 1): cada producto tiene UNA categoría
    id_categoria  INT           NOT NULL,
    precio        DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (id_producto),
    -- Índice para optimizar el JOIN:
    INDEX idx_categoria (id_categoria),
    CONSTRAINT fk_producto_categoria
        FOREIGN KEY (id_categoria)
        REFERENCES categorias (id_categoria)
        ON DELETE RESTRICT   -- no borrar categorías con productos
        ON UPDATE CASCADE
);

N : M Relación Muchos a Muchos — La más poderosa

Muchos registros de A se relacionan con muchos de B, y viceversa. En TechPlay Store: una venta incluye muchos productos, y un producto aparece en muchas ventas.

⚠️ Las relaciones N:M NO existen directamente en SQL
No podés implementarlas entre dos tablas directamente. La solución universal es crear una Tabla Intermedia (tabla puente / junction table). Tiene como mínimo dos FK, una hacia cada tabla principal.

La tabla detalle_ventas implementa la N:M. Dos relaciones 1:N convergen en ella.

⚡ Camino A — Automático

Seleccioná M:N Non-Identifying y hacé clic en las dos tablas. Workbench crea la tabla intermedia con campos mínimos. Útil para aprender el concepto rápido.

✅ Camino B — Manual (recomendado)

Creás la tabla intermedia con todos los campos del negocio (cantidad, precio…), luego establecés dos relaciones 1:N por separado.

-- Tabla INTERMEDIA: implementa la N:M entre ventas y productos
CREATE TABLE detalle_ventas (
    id_detalle      INT           AUTO_INCREMENT NOT NULL,
    id_venta        INT           NOT NULL,   -- FK → ventas
    id_producto     INT           NOT NULL,   -- FK → productos
    cantidad        INT           NOT NULL,
    precio_unitario DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (id_detalle),
    INDEX idx_venta    (id_venta),
    INDEX idx_producto (id_producto),
    -- Primera FK: cada detalle pertenece a UNA venta
    CONSTRAINT fk_detalle_venta
        FOREIGN KEY (id_venta)
        REFERENCES ventas (id_venta)
        ON DELETE CASCADE ON UPDATE CASCADE,
    -- Segunda FK: cada detalle referencia UN producto
    CONSTRAINT fk_detalle_producto
        FOREIGN KEY (id_producto)
        REFERENCES productos (id_producto)
        ON DELETE RESTRICT ON UPDATE CASCADE
);

USE techplay;

CREATE TABLE datos_tecnicos_consolas (
    id_tecnico     INT         AUTO_INCREMENT NOT NULL,
    id_producto    INT         NOT NULL,
    resolucion_max VARCHAR(20) NULL,

        FOREIGN KEY (id_producto)
        REFERENCES productos (id_producto)
        ON DELETE CASCADE ON UPDATE CASCADE
);

SELECT p.nombre, p.precio, t.resolucion_max, t.chip_grafico, t.consumo_watts

TP N° 6 — Sucursales y Métodos de Pago

Dos nuevas relaciones 1:N expanden la tabla ventas · 80–90 min.

›
🏪 Problema de Negocio
TechPlay Store abre 2 sucursales nuevas (Posadas y Puerto Iguazú). El sistema debe registrar en qué sucursal se realizó cada venta y qué método de pago se usó (efectivo, débito, crédito, MODO). Ambas son relaciones 1:N con la tabla ventas.

0 / 5

Script SQL esperado

USE techplay;

CREATE TABLE sucursales (
    id_sucursal     INT         AUTO_INCREMENT NOT NULL,
    nombre_sucursal VARCHAR(80) NOT NULL,
    ciudad          VARCHAR(60) NOT NULL,
    activa          TINYINT(1)  NOT NULL DEFAULT 1,
    PRIMARY KEY (id_sucursal)
);

CREATE TABLE metodos_pago (
    id_metodo          INT          AUTO_INCREMENT NOT NULL,
    nombre_metodo      VARCHAR(40)  NOT NULL,
    recargo_porcentaje DECIMAL(4,2) NOT NULL DEFAULT 0.00,
    PRIMARY KEY (id_metodo)
);

ALTER TABLE ventas
    ADD COLUMN id_sucursal    INT NOT NULL DEFAULT 1,
    ADD COLUMN id_metodo_pago INT NOT NULL DEFAULT 1,
    ADD CONSTRAINT fk_venta_sucursal
        FOREIGN KEY (id_sucursal)
        REFERENCES sucursales (id_sucursal)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    ADD CONSTRAINT fk_venta_metodo
        FOREIGN KEY (id_metodo_pago)
        REFERENCES metodos_pago (id_metodo)
        ON DELETE RESTRICT ON UPDATE CASCADE;

-- 4 JOINs de verificacion:
SELECT v.id_venta, CONCAT(c.nombre,' ',c.apellido) AS cliente,
       s.nombre_sucursal, mp.nombre_metodo
FROM ventas v
INNER JOIN clientes     c  ON v.id_cliente     = c.id_cliente
INNER JOIN sucursales   s  ON v.id_sucursal    = s.id_sucursal
INNER JOIN metodos_pago mp ON v.id_metodo_pago = mp.id_metodo;

TP N° 7 — Modulo de Promociones Especiales

Relacion N:M con tabla intermedia + consultas analiticas · 90–120 min.

›
Problema de Negocio
Marketing quiere promociones de fin de anio. Reglas: una promo incluye varios productos; un producto puede estar en varias promos. Cada combinacion tiene su propio descuento. Esto define una relacion N:M entre promociones y productos.

Objetivos

0 / 4
Reflexion clave: LEFT JOIN y COALESCE
Usamos LEFT JOIN entre detalle_ventas y promociones_productos para ver TODAS las ventas, incluso las que ocurrieron fuera de cualquier periodo de promo. COALESCE(pp.precio_promo, dv.precio_unitario) devuelve el precio_promo si existe, o el precio real si no hubo promo activa.

Script SQL esperado

CREATE TABLE promociones (
    id_promocion INT AUTO_INCREMENT NOT NULL,
    nombre_promo VARCHAR(100) NOT NULL,
    fecha_inicio DATE NOT NULL,
    fecha_fin    DATE NOT NULL,
    activa       TINYINT(1) NOT NULL DEFAULT 1,
    PRIMARY KEY (id_promocion)
);

CREATE TABLE promociones_productos (
    id_promo_prod        INT AUTO_INCREMENT NOT NULL,
    id_promocion         INT NOT NULL,
    id_producto          INT NOT NULL,
    descuento_porcentaje DECIMAL(5,2) NOT NULL,
    precio_promo         DECIMAL(10,2) NULL,
    PRIMARY KEY (id_promo_prod),
    UNIQUE INDEX uq_pp (id_promocion, id_producto),
    CONSTRAINT fk_pp_promo
        FOREIGN KEY (id_promocion) REFERENCES promociones(id_promocion)
        ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT fk_pp_prod
        FOREIGN KEY (id_producto) REFERENCES productos(id_producto)
        ON DELETE RESTRICT ON UPDATE CASCADE
);

-- Productos con promo activa HOY:
SELECT p.nombre, p.precio AS normal, pr.nombre_promo,
       pp.descuento_porcentaje, pp.precio_promo
FROM productos p
INNER JOIN promociones_productos pp ON p.id_producto  = pp.id_producto
INNER JOIN promociones           pr ON pp.id_promocion = pr.id_promocion
WHERE pr.activa = 1 AND CURDATE() BETWEEN pr.fecha_inicio AND pr.fecha_fin
ORDER BY pp.descuento_porcentaje DESC;
